# Requirements Document

## Introduction

This feature introduces two architectural changes to the ICAv2 WES Manager service:

1. **Decouple Callback Unlock from Launch SFN Lifecycle** — Currently, the `generate_wes_post_request_from_event` Lambda calls the WES Manager's own API (`Create_Job_API`) to create an analysis, registers a callback ID in the Callback_Table with `id_type=LAUNCH_REQUEST`, and waits for the callback to be unlocked. The callback is currently unlocked at the END of the `launch_icav2_analysis_sfn` (after ICA API call + payload DB write). Instead, the Generate_Wes_Post_Request_Lambda SHALL pass its callback token directly in the Create_Job_API request body. The Create_Job_API SHALL then invoke the Unlock_Callback_Mechanism (via the unlock-callback-id SFN) with the provided token immediately after setting the analysis status to SUBMITTED. This eliminates the need for any Callback_Table lookup — the token flows directly from the caller to the unlock mechanism.

2. **API Rate-Limiting via Launch Queue** — The `create_job` API endpoint currently directly invokes the `launch_icav2_analysis_sfn` Step Function. Instead, it should enqueue the job to a new Launch_Analysis_Queue (SQS). A rate-limited consumer Lambda reads from this queue and invokes the SFN. This prevents bursts of API requests from overwhelming the external ICA service.

The resulting architecture has two separate queues:

- **WES_Request_Event_Queue** (existing) → `generate_wes_post_request_from_event` → calls Create_Job_API → callback unlocked immediately after SUBMITTED status
- **Launch_Analysis_Queue** (new) → rate-limited consumer Lambda → `launch_icav2_analysis_sfn` → ICA API

## Glossary

- **Create_Job_API**: The FastAPI `POST /api/v1/analyses/` endpoint that creates a new ICAv2 WES analysis record, generates a ULID, sets status to SUBMITTED, enqueues to the Launch_Analysis_Queue, invokes the unlock-callback-id SFN with the provided callback token, and returns immediately
- **Launch_Analysis_SFN**: The `launch_icav2_analysis_sfn` Step Function that updates status to RUNNABLE, submits an analysis to the ICA_API via a Lambda, and writes to the payloads database
- **Launch_Analysis_Queue**: A new SQS queue placed between the Create_Job_API and the Launch_Queue_Consumer_Lambda, providing rate-limited delivery to the Launch_Analysis_SFN
- **Launch_Queue_Consumer_Lambda**: A new rate-limited Lambda that consumes messages from the Launch_Analysis_Queue and invokes the Launch_Analysis_SFN
- **Callback_Table**: The DynamoDB table (`icav2WesManagerCallbackTable`) used to store callback IDs for the durable execution wait-for-callback pattern
- **Callback_Token**: The task token generated by the durable execution SDK's `wait_for_callback` mechanism in the Generate_Wes_Post_Request_Lambda. This token is passed directly to the Create_Job_API in the request body, eliminating the need for a Callback_Table lookup during unlock
- **Generate_Wes_Post_Request_Lambda**: The existing `generate_wes_post_request_from_event` Lambda that consumes WES request events from the WES_Request_Event_Queue. It calls the Create_Job_API via `orcabus_api_tools.icav2_wes.create_icav2_wes_analysis()`, passing its callback token in the request body, and waits for the callback to be unlocked
- **Unlock_Callback_SFN**: The `unlock-callback-id` Step Function that accepts a callback token as input and invokes the `unlock_callback_id` Lambda to send a task success signal, releasing the waiting Generate_Wes_Post_Request_Lambda
- **WES_Request_Event_Queue**: The existing SQS queue that delivers `Icav2WesRequest` events to the Generate_Wes_Post_Request_Lambda
- **ICA_API**: The external Illumina Connected Analytics v2 API
- **Event_Source_Mapping**: The AWS Lambda event source mapping configuration that connects an SQS queue to a Lambda function with concurrency controls
- **ULID**: The unique identifier (orcabus ID) generated by the WES API when an analysis record is created

## Requirements

### Requirement 1: Decouple Callback Unlock from Launch SFN Lifecycle

**User Story:** As a platform operator, I want the callback registered by the Generate_Wes_Post_Request_Lambda to be unlocked immediately after the Create_Job_API sets the analysis status to SUBMITTED, so that the event-sourced Lambda is released without waiting for the full ICA submission lifecycle.

#### Acceptance Criteria

1. THE Create_Job_API request schema SHALL accept an optional `callbackToken` string field in the request body
2. WHEN the Generate_Wes_Post_Request_Lambda receives a WES request event, THE Generate_Wes_Post_Request_Lambda SHALL call the Create_Job_API passing its durable execution callback token in the `callbackToken` field of the request body
3. THE Generate_Wes_Post_Request_Lambda SHALL wait for the callback to be unlocked AND complete its message processing before finishing, with a maximum wait timeout of 15 minutes, after which the Lambda SHALL treat the message as failed
4. WHEN the Create_Job_API sets the analysis status to SUBMITTED and a `callbackToken` is present in the request, THE Create_Job_API SHALL invoke the Unlock_Callback_SFN asynchronously (fire-and-forget) with the provided callback token, without blocking the API response to the caller
5. WHEN the Create_Job_API sets the analysis status to SUBMITTED and no `callbackToken` is present in the request (direct API call), THE Create_Job_API SHALL proceed without invoking the Unlock_Callback_SFN
6. IF the Create_Job_API call fails, THEN THE Generate_Wes_Post_Request_Lambda SHALL propagate the failure to the WES_Request_Event_Queue by not deleting the message, allowing standard SQS retry behaviour
7. THE Generate_Wes_Post_Request_Lambda SHALL NOT register callback IDs in the Callback_Table for the LAUNCH_REQUEST id_type, as the callback token is passed directly to the Create_Job_API

### Requirement 2: API Rate-Limiting via Launch Queue

**User Story:** As a platform operator, I want the Create_Job_API to enqueue jobs to a launch queue instead of directly invoking the Step Function, so that burst API traffic is rate-limited before reaching the ICA API.

#### Acceptance Criteria

1. THE Launch_Analysis_Queue SHALL be a standard SQS queue with a dead-letter queue configured with a maxReceiveCount of 3
2. WHEN the Create_Job_API creates a new analysis record, THE Create_Job_API SHALL enqueue the job to the Launch_Analysis_Queue instead of directly invoking the Launch_Analysis_SFN
3. THE Create_Job_API SHALL include the analysis orcabus ID, name, inputs, engineParameters, and tags as a JSON-serialized SQS message body
4. THE Launch_Analysis_Queue SHALL have a visibility timeout of at least 6 times the Launch_Queue_Consumer_Lambda timeout
5. IF a message fails processing after 3 receive attempts, THEN THE Launch_Analysis_Queue SHALL route the message to the dead-letter queue
6. IF the Create_Job_API fails to enqueue the message to the Launch_Analysis_Queue, THEN THE Create_Job_API SHALL return an error response and SHALL NOT set the analysis status to SUBMITTED

### Requirement 3: Rate-Limited Launch Queue Consumer Lambda

**User Story:** As a platform operator, I want a concurrency-controlled Lambda consuming the launch queue, so that the number of concurrent ICA API requests is bounded regardless of traffic volume.

#### Acceptance Criteria

1. THE Launch_Queue_Consumer_Lambda SHALL use the durable execution `wait_for_callback` pattern to hold its concurrency slot while the Launch_Analysis_SFN is executing
2. WHEN the Launch_Queue_Consumer_Lambda receives a message from the Launch_Analysis_Queue, THE Launch_Queue_Consumer_Lambda SHALL start an execution of the Launch_Analysis_SFN with the analysis payload containing the analysis orcabus ID, name, inputs, engineParameters, tags, and the Lambda's own callback token
3. THE Launch_Queue_Consumer_Lambda SHALL wait for the Launch_Analysis_SFN to unlock its callback token before completing message processing, with a maximum wait timeout sufficient to accommodate the Launch_Analysis_SFN execution duration
4. THE Event_Source_Mapping for the Launch_Queue_Consumer_Lambda SHALL be configured with a batch size of 1 and a maximum concurrency equal to the configured ICA API concurrency constraint, so that each concurrent Lambda invocation corresponds to exactly one ICA API submission
5. IF the Launch_Queue_Consumer_Lambda fails to invoke the Launch_Analysis_SFN, THEN THE Launch_Queue_Consumer_Lambda SHALL both log the failure and delete the message from the Launch_Analysis_Queue; the Lambda SHALL only complete successfully when both operations succeed

### Requirement 4: Asynchronous Callback Unlock via Token

**User Story:** As a platform operator, I want the Unlock_Callback_SFN to accept a callback token directly and invoke the unlock_callback_id Lambda, so that callbacks are unlocked without any database lookup overhead.

#### Acceptance Criteria

1. THE Unlock_Callback_SFN SHALL accept a callback token as its input parameter
2. WHEN invoked, THE Unlock_Callback_SFN SHALL invoke the unlock_callback_id Lambda with the provided callback token to send a task success signal
3. IF the unlock_callback_id Lambda fails to send the task success signal due to an expired or invalid task token, THEN THE Unlock_Callback_SFN SHALL complete without raising an error, even if logging the failure also fails
4. THE Unlock_Callback_SFN SHALL NOT perform any Callback_Table lookups or deletions — it operates solely on the provided callback token

### Requirement 5: Launch Analysis SFN Callback Token Handling

**User Story:** As a platform operator, I want the Launch_Analysis_SFN to unlock the Launch_Queue_Consumer_Lambda's callback token upon completion, so that the consumer Lambda's concurrency slot is released and the rate-limiting constraint is enforced for the duration of ICA API interaction.

#### Acceptance Criteria

1. THE Launch_Analysis_SFN SHALL accept an optional `callbackToken` field in its input payload, provided by the Launch_Queue_Consumer_Lambda
2. THE Launch_Analysis_SFN SHALL execute the following steps in order on the success path: update the analysis status to RUNNABLE via the WES API, call the ICA_API to submit the analysis, write to the payloads database, and then invoke the unlock_callback_id Lambda with the provided callback token
3. WHEN the Launch_Analysis_SFN completes successfully and a `callbackToken` is present in the input, THE Launch_Analysis_SFN SHALL invoke the unlock_callback_id Lambda with the provided callback token to release the waiting Launch_Queue_Consumer_Lambda
4. WHEN the Launch_Analysis_SFN completes successfully and no `callbackToken` is present in the input, THE Launch_Analysis_SFN SHALL terminate without invoking the unlock_callback_id Lambda
5. WHEN the Launch_Analysis_SFN fails to submit the analysis to the ICA_API, THE Launch_Analysis_SFN SHALL immediately update the analysis status to FAILED via the WES API including the error type and error message, and then invoke the unlock_callback_id Lambda with the provided callback token before terminating
6. IF the Launch_Analysis_SFN fails to update the analysis status to FAILED after an ICA_API submission failure, THEN THE Launch_Analysis_SFN SHALL still attempt to unlock the callback token before failing the execution
7. THE Launch_Analysis_SFN SHALL NOT look up callback IDs from the Callback_Table — it SHALL only use the callback token provided directly in its input

### Requirement 6: Failure Handling and Observability

**User Story:** As a platform operator, I want failures in the rate-limiting pipeline to be visible and recoverable, so that failed submissions can be diagnosed and retried.

#### Acceptance Criteria

1. IF a message reaches the dead-letter queue, THEN THE monitoring system SHALL trigger a CloudWatch alarm when the ApproximateNumberOfMessagesVisible metric for the dead-letter queue exceeds 0 for 1 or more consecutive evaluation periods
2. WHEN the Launch_Analysis_SFN fails to submit an analysis to the ICA_API, THE Launch_Analysis_SFN SHALL update the analysis status to FAILED via the WES API, including the error type and error message from the failed submission attempt
3. THE Launch_Analysis_Queue SHALL retain failed messages in the dead-letter queue for a minimum of 14 days for post-mortem analysis
4. THE Launch_Analysis_Queue SHALL route messages to the dead-letter queue after a maximum of 3 receive attempts
5. WHEN a platform operator initiates a retry of a message from the dead-letter queue, THE Launch_Analysis_Queue SHALL accept the re-driven message for standard processing through the Launch_Queue_Consumer_Lambda regardless of current downstream conditions such as rate limits or service availability
